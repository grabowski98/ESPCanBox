# Напишіть профіль автомобіля

> [!NOTE]
> **Машинний переклад, потребує перевірки**
>
> Цю сторінку перекладено автоматично. Обов'язковим є англійський текст. Як надіслати
> виправлення: [Переклади](../../en/contributing/translations.md#send-your-work).

**Профіль автомобіля** пояснює прошивці, як читати один автомобіль: швидкість шини, які біти є
кнопками на кермі, де запалювання, задня передача, фари та парктроніки. Це одна константна
структура на C++ (`vehicle::CarProfile`, визначена у `firmware/lib/core/car_profile.h`),
вкомпільована в програму. Ви вибираєте профіль, коли збираєте прошивку; поки пристрій працює,
змінити його не можна.

Ця сторінка веде вас від декодованих кадрів до профілю, який збирається. Наступна сторінка,
[Перевірте свій профіль](test-your-profile.md), перевіряє його на записі на вашому ПК.

Кожен крок на цій сторінці пробували на копії репозиторію з вигаданим автомобілем. Де щось пішло
не так, сторінка про це каже й показує повідомлення, яке ви побачите.

> [!CAUTION]
> **Власний профіль лише прослуховує шину автомобіля**
>
> Профіль, зібраний з `-DCAR_PROFILE=CUSTOM`, ніколи не може передавати на шину CAN автомобіля.
> Середовище з передачею `decoder_tx_wifi` відмовляється збиратися з ним і зупиняється з
> `CAN transmit is not allowed with CAR_PROFILE=CUSTOM (listen-only; add a named profile in src/config.h)`.
> Не намагайтеся це обійти. Передача для нового автомобіля потребує виміряних кадрів, перевірок
> вмісту, написаних у коді, і тестів: див. [Передача на шину CAN](../../en/safety/transmit.md).

## Що покриває профіль {#what-a-profile-covers}

Майте це на увазі, перш ніж почати. Профіль несе лише частину того, що пристрій робить на еталонному
автомобілі (Peugeot 508 SW 2015, профіль `psa_aee2010`).

| Функція | Через ваш профіль | Примітки |
|---|---|---|
| Швидкість шини | так | `canBitrate` |
| Кнопки на кермі й панелі, поворотні ручки | так | таблиці `keys` і `knobs` |
| Стан запалювання і двигуна, задня передача | так | функція `decodeBody`; керує ACC і виходом задньої передачі |
| Фари ввімкнено | так | функція `decodeLights`; керує виходом підсвічування |
| Парктроніки і звуковий сигнал з динаміка пристрою | так | функція `decodeParking` |
| Список дозволених кадрів | **ні**: поле залишається порожнім (`nullptr, 0`) | профіль `CUSTOM` не може передавати (див. вище) |
| Кадри, що містять VIN | перелічено, інформаційно | `privacyIds`; прошивка цього не використовує |
| Двері, багажник і капот | так | функція `decodeDoors` -> `vehicle::DoorState` |
| Бортовий комп'ютер | так, з обмеженням | функція `decodeTrip` -> `vehicle::TripData`. Значення зберігають кодування еталонного автомобіля (їхній зміст не перевірено): заповнюйте їх, лише якщо ваш автомобіль використовує таке саме |
| Зовнішня температура, економний режим | так | функції `decodeOutsideTemp`, `decodeEcoMode` |
| Стан клімат-контролю | так | функція `decodeClimate` -> `vehicle::ClimateState` |
| Кут повороту керма | так, з обмеженням | функція `decodeSteering`; масштаб на еталонному автомобілі не перевірено |
| Налаштування автомобіля (те, що показує магнітола) | так | функція `decodeSettings` -> `vehicle::VehicleSettings` (пункти з нейтральними ідентифікаторами) |
| Зміна налаштування автомобіля з магнітоли | **ні** | лише еталонний профіль `psa_aee2010`, за шлюзом передачі |

Дані автомобіля для екрана магнітоли (від дверей до налаштувань автомобіля) необов'язкові:
залиште вказівник `nullptr`, і магнітола ніколи не отримає ці дані. Кожна функція заповнює
нейтральний тип з `firmware/lib/core/vehicle_signals.h`; протокол магнітоли перетворює його на свій
кадр. Їх перелічує підрозділ «Дані автомобіля для екрана магнітоли» у кроці 3.

Тож з протоколом магнітоли XP профіль іншого автомобіля дає магнітолі: стан живлення (ACC),
натискання кнопок, зображення парктроніків, прапорець перешкоди і всі функції даних автомобіля,
які заповнив профіль. Зміна налаштувань автомобіля з магнітоли лишається за еталонним автомобілем.

## Перш ніж почати {#before-you-start}

Вам потрібні:

- швидкість передачі, дроти CAN і тип шини вашого автомобіля ([Знайдіть свою шину](find-your-bus.md));
- запис з маркерами ([Запишіть шину](record.md));
- кадри й біти, які ви декодували ([Декодуйте кадри](decode.md)). Запишіть кожен зі статусом,
  **виміряно** (measured) або **не перевірено** (unverified), у копію `vehicles/_template/README.md`;
- інструменти збирання зі сторінки [Прошивка](../quick-start/flash.md): `uv` і, у Windows,
  Git Bash.

Вам не потрібен кожен сигнал. Профіль лише із запалюванням уже корисний: він може перемикати ACC
магнітоли. Пропустіть усе, чого ви не виміряли.

## Крок 1: скопіюйте шаблон {#step-1-copy-the-template}

Шаблон `firmware/lib/car_example/` описує вигаданий автомобіль з коментарями до кожного поля. Його
компілюють лише тести на комп'ютері, і він ніколи не потрапляє в прошивку.

> [!NOTE]
> **Два вигадані автомобілі**
>
> Шаблон використовує кадри `100`, `200`, `300` і `400`. Приклади на цій сторінці та на сторінці
> [Перевірте свій профіль](test-your-profile.md) взято з **другого** вигаданого автомобіля,
> «навчального автомобіля» (кадри `2C0`, `1F0`, `350`, `2C8`), придуманого, коли ці сторінки
> випробовували. Його запису немає в репозиторії; фрагменти лише показують, як виглядають ваші
> власні значення. У своїй копії ви замінюєте значення шаблону кадрами свого автомобіля.

Виберіть коротку назву для профілю, малими літерами, наприклад `mine`. Потім відкрийте Git Bash
у теці `firmware`: у Провіднику відкрийте цю теку, клацніть правою кнопкою миші й виберіть
«Open Git Bash here» (у Windows 11 у пункті «Показати додаткові параметри»). Виконайте:

```bash
cp -r lib/car_example lib/car_mine
cd lib/car_mine
mv profile_example.h profile_mine.h
mv profile_example.cpp profile_mine.cpp
cd ../..
```

Назви файлів мають бути унікальними в усьому `firmware/lib/`: усі бібліотеки мають один спільний
шлях include, а `tools/check_layering.py` повідомляє про назву заголовного файлу, що трапляється
двічі.

## Крок 2: перейменуйте всередині файлів {#step-2-rename-inside-the-files}

Відкрийте три файли в текстовому редакторі й перейменуйте:

| Де | З | На |
|---|---|---|
| `profile_mine.cpp`, перший `#include` | `"profile_example.h"` | `"profile_mine.h"` |
| обидва файли | `kCarExample` | `kCarMine` |
| обидва файли | `namespace example` і `example::` | `namespace mine` і `mine::` |
| `profile_mine.cpp`, перше поле профілю | `"example"` | `"mine"` |
| `library.json`, поле `name` | `"car_example"` | `"car_mine"` |
| `library.json`, поле `description` | текст шаблону | один рядок про ваш автомобіль |

> [!WARNING]
> **Не забудьте про `library.json`**
>
> PlatformIO знає бібліотеку за `name` у `library.json`, а не за назвою теки. Середовища
> `listen` ігнорують бібліотеку з назвою `car_example` (`lib_ignore` у
> `firmware/platformio.ini`). Зі старою назвою збирання завершується помилкою
> `Warning! Could not find the package with 'car_mine' requirements`, а потім
> `fatal error: profile_mine.h: No such file or directory`.

## Крок 3: заповніть профіль {#step-3-fill-in-the-profile}

Працюйте в такому порядку:

1. У `profile_mine.h` задайте чотири ID кадрів `ID_BODY`, `ID_KEYS`, `ID_PARKING` і
   `ID_LIGHTS` рівними кадрам вашого автомобіля. ID, функцію якого ви задасте як `nullptr`
   (пункт 4), не читається.
2. У `profile_mine.cpp` перепишіть функції `decodeBody`, `decodeParking` і `decodeLights`
   (розділи нижче).
3. У тому самому файлі заповніть таблиці `KEYS` і `KNOBS` (розділи нижче).
4. У кінці файлу заповніть константу профілю (таблиця нижче). Її поля в коді не мають назв,
   важить лише порядок, тож залиште коментар біля кожного рядка.

Хочете перевірити копію й перейменування, перш ніж змінювати будь-які значення? Спершу зробіть
пробний прогін зі сторінки [Перевірте свій профіль](test-your-profile.md).

Поля константи профілю по порядку:

| Поле | Що туди вписати |
|---|---|
| `id` | коротка назва ASCII, показується в консолі (`# profile: car=mine radio=xp`) і в панелі |
| `canBitrate` | виміряна швидкість передачі в bit/s |
| `physicalLayer` | `vehicle::PhysicalLayer::UNKNOWN`, `HIGH_SPEED` або `LOW_SPEED_FT`. Лише інформаційно: трансивер визначає плата. Лишайте `UNKNOWN`, доки не виміряєте |
| `keys`, `keyCount` | таблиця кнопок (нижче); `nullptr, 0`, якщо немає |
| `knobs`, `knobCount` | таблиця ручок (нижче); `nullptr, 0`, якщо немає |
| `txAllow`, `txAllowCount` | `nullptr, 0`. Профіль `CUSTOM` ніколи не передає |
| `privacyIds`, `privacyCount` | ідентифікатори кадрів, що містять VIN у вашому автомобілі, якщо ви їх знаєте; інакше `nullptr, 0` |
| `decodeParking` | ваша функція парктроніків або `nullptr` |
| `decodeBody` | ваша функція запалювання й задньої передачі або `nullptr` |
| `decodeLights` | ваша функція фар або `nullptr` |
| `powerOutputs` | `true` лише тоді, коли `decodeBody` надійно читає запалювання; `false` тримає всі виходи 12 V вимкненими |
| `keyRemapDefaults`, `keyRemapDefaultCount` | `nullptr, 0`: кожна кнопка доходить до магнітоли зі своїм кодом. Рядки `{from, to}` (коди XP) лише для перепризначень, які потрібні типово; див. [Зіставте кнопки з магнітолою](radio-mapping.md#default-remappings-come-from-the-car-profile) |

`nullptr` дозволено завжди: тоді цей сигнал ніколи не формується.

### Номери байтів у коді починаються з 0 {#byte-numbers-in-code-start-at-0}

Документація і сторінки автомобілів рахують байти CAN від **1** (байт 1 = перший байт даних). У
C++ перший байт — це `f.data[0]`, і поле `byteIndex` таблиць — той самий індекс. Тож кнопка, яку
ви записали як «байт 1, біт 2», — це `byteIndex 0, mask 0x04`. Перевірте це двічі: цю
помилку зробити найлегше.

### Швидкість передачі {#bit-rate}

`src/can_bus.cpp` знає такі швидкості: 50000, 100000, 125000, 250000, 500000 і 1000000 bit/s.
Будь-яке інше значення компілюється, але контролер CAN не запускається: консоль показує
`# can=FAIL`, світлодіод стану стає червоним, а виходи 12 V лишаються вимкненими. Це безпечний
стан, а не збій.

### Запалювання і задня передача: `decodeBody` {#ignition-and-reverse-decodebody}

Функція отримує кожен прийнятий кадр. Вона повертає `false` для будь-якого чужого кадру або
надто короткого, і `true` після того, як заповнила `out`. Завжди спершу перевіряйте
ідентифікатор і довжину; ніколи не читайте за межами довжини.

Прошивка не використовує байт запалювання вашого автомобіля напряму. Ви перетворюєте його на
незалежний від автомобіля `vehicle::Ignition` (`firmware/lib/core/vehicle_signals.h`):

| Значення | Що означає |
|---|---|
| `OFF` | запалювання вимкнено або ще нічого не декодовано |
| `ON` | запалювання ввімкнено, двигун не працює |
| `ENGINE` | двигун працює |
| `TRANSITION` | будь-що інше, що не є вимкненням: прокручування стартером, вимикання, значення, якого ви не знаєте |

Сире значення вашого автомобіля зберігайте в `ignitionRaw`. Воно лише показується в консолі та
в панелі.

Приклад з вигаданого автомобіля цього посібника (кадр `2C0`: байт 2 = запалювання, байт 4 біт 6 =
задня передача):

```cpp
bool decodeBody(const CanFrame& f, vehicle::BodyState& out) {
    if (f.id != ID_BODY || f.len < 4) return false;   // our frame, long enough?
    out.ignitionRaw = f.data[1];                       // byte 2
    switch (f.data[1]) {
        case 0: out.ignition = vehicle::Ignition::OFF; break;
        case 1: out.ignition = vehicle::Ignition::ON; break;
        case 2: out.ignition = vehicle::Ignition::ENGINE; break;
        default: out.ignition = vehicle::Ignition::TRANSITION; break;
    }
    out.reverseGear = (f.data[3] & 0x40) != 0;         // byte 4 bit 6
    return true;
}
```

Як це використовує загальна логіка (`firmware/lib/core/power_policy.h`):

- ACC увімкнено в кожному стані, крім `OFF`, тож прокручування стартером не вимикає магнітолу.
- ACC вимикається через 2.5 s після того, як запалювання переходить у `OFF`.
- Кадр має надходити постійно. Якщо його немає понад 1 s, запалювання вважається вимкненим
  ([як виміряти період](decode.md#how-often-a-frame-comes)). На
  еталонному автомобілі кадр запалювання `0F6` надходить кожні 500 ms (виміряно (measured): запис
  `can_20261111_191045.log`). Якщо ваш кадр запалювання надходить рідше, ніж раз на секунду,
  виходи 12 V вимикатимуться.
- Вихід задньої передачі ввімкнений лише з увімкненим запалюванням і свіжим кадром.

### Фари: `decodeLights` {#lights-decodelights}

Той самий шаблон: перевірте ідентифікатор і довжину, встановіть `lightsOn`, поверніть `true`.
Вихід підсвічування ввімкнений лише тоді, коли запалювання ввімкнено **і** кадр фар надійшов
протягом останньої секунди ([як виміряти період](decode.md#how-often-a-frame-comes)). Автомобіль, який надсилає стан фар лише при зміні, втратить вихід
підсвічування через одну секунду.

### Парктроніки: `decodeParking` {#parking-sensors-decodeparking}

Заповніть `vehicle::ParkingState` з тим самим значенням полів, що й на еталонному автомобілі:

| Поле | Що означає |
|---|---|
| `rearStatus`, `frontStatus` | `4` (`PARK_ACTIVE`) = працює. Зумер використовує лише сторону зі статусом 4. Інші значення: 1 несправність, 2 вимкнено водієм, 5 очікування, 6 не працює |
| `rearLeft` ... `frontRight` | зони 0–7: 0 = дуже близько, 7 = далеко або немає перешкоди. Обмежте свої значення діапазоном 0..7 |
| `soundRequest`, `soundFront` | автомобіль просить звук; спереду (`true`) чи ззаду |
| `intervalRaw` | `0x00` = безперервний сигнал, `0x3F` = без сигналів, значення між ними = все ближче й ближче |

Почніть з `out = vehicle::ParkingState();`, щоб кожне поле, яке ви не заповнюєте, мало своє
значення «нічого» (зони 7, статус 0).

Що пристрій з цим робить (`firmware/lib/core/parking_beeper.h`):

- він подає сигнал з першої зони нижче 7 на активній стороні, навіть якщо автомобіль не просить
  звуку; темп береться з найближчої зони;
- він грає безперервний сигнал **лише** тоді, коли встановлено `soundRequest`, а `intervalRaw`
  дорівнює `0x00`. Якщо ваш автомобіль не повідомляє інтервал, обчисліть його із зони, як це робить
  шаблон;
- він замовкає, коли кадр парктроніків не надходив 400 ms. На еталонному автомобілі кадр
  надходить кожні 100 ms.

### Дані автомобіля для екрана магнітоли {#car-data-for-the-radio-screen}

Сім необов'язкових функцій, усі з однаковими правилами: спершу перевірте ID і довжину, заповніть
нейтральний тип, встановіть його прапорець `valid`, поверніть `true` (або біти сторінки чи зміни).
`firmware/lib/car_example/profile_example.cpp` показує `decodeDoors` і `decodeTrip`.

- `decodeDoors` -> `DoorState`: `open` містить біти `DOOR_DRIVER`, `DOOR_PASSENGER`,
  `DOOR_REAR_LEFT`, `DOOR_REAR_RIGHT`, `DOOR_BOOT`, `DOOR_BONNET`; `anyOpen` = попередження
  автомобіля про відчинені двері. Повертайте `true`, лише коли кадр щось повідомляє про двері.
- `decodeTrip` -> `TripData`: поверніть `TRIP_NOW`, `TRIP_1` або `TRIP_2` для сторінки, яку
  оновив кадр.
- `decodeOutsideTemp` -> `OutsideTemp`, у половинах градуса Цельсія.
- `decodeEcoMode` -> `EcoMode`: автомобіль ось-ось вимкне споживачі.
- `decodeClimate` -> `ClimateState`: температури в половинах градуса (0 = немає значення),
  вентилятор 0..15, прапорці `AIR_*`.
- `decodeSteering` -> `SteeringAngle`: сире значення в кодуванні еталонного автомобіля.
- `decodeSettings` -> `VehicleSettings`: для кожного пункту `at(SettingId::...)` значення `value`,
  `known` (ваш останній кадр його повідомив) і `present` / `presentKnown` (автомобіль має цей
  пункт). Поверніть `SETTINGS_VALUES` і / або `SETTINGS_PRESENT`.

Функції з аргументом `io` (бортовий комп'ютер, клімат-контроль, двері, налаштування) отримують
стан, який декодер зберігає між кадрами. Змінюйте лише те, що повідомляє ваш кадр, щоб кілька
кадрів могли скласти один стан.

### Кнопки: таблиця `keys` {#buttons-the-keys-table}

Один рядок — це одна кнопка, яка «натиснута, поки присутній шаблон бітів»:

```cpp
{canId, byteIndex, mask, value, KeyId::...}
```

Кнопка вважається натиснутою, поки `(data[byteIndex] & mask) == value` у кадрі `canId`. Правила з
коду (`firmware/lib/core/car_profile.h`, `firmware/lib/app/xp_keys.h`):

- порядок рядків — це порядок зіставлення і порядок подій для магнітоли;
- використовується не більше 32 рядків;
- кадр, коротший за `byteIndex + 1`, для цього рядка пропускається;
- рядок, шаблон якого присутній, коли нічого не натиснуто, повідомляє про кнопку, утримувану весь
  час. Зі `value` = `0x00` це стається легко; дайте кожному рядку шаблон, який дає лише натискання;
- натискання = одна подія одразу, потім кожні 200 ms «утримується», поки шаблон лишається, потім
  «відпущено».

Два способи, якими автомобіль може кодувати кнопки, обидва трапляються на практиці:

```cpp
// one bit per button (template car: byte 1 bit 0 = volume +, bit 1 = volume -)
{0x200, 0, 0x01, 0x01, KeyId::VOLUME_UP},
{0x200, 0, 0x02, 0x02, KeyId::VOLUME_DOWN},

// a button number in a group of bits (tutorial car: byte 1 bits 3-0 = 1, 2, 3, ...)
{0x1F0, 0, 0x0F, 0x01, KeyId::VOLUME_UP},
{0x1F0, 0, 0x0F, 0x02, KeyId::VOLUME_DOWN},
```

Еталонний профіль теж використовує другий спосіб: у кадрі `21F` байт 1 маска `0C` дає гучність +
(`08`), гучність - (`04`) і обидві разом, вимкнення звуку (`0C`) (виміряно: записи
`can_20261111_190817.log` і `can_20261111_191045.log`, CAN і лінія CAN-адаптера до магнітоли на
спільній шкалі часу).

Назви (`KeyId`) — це логічні кнопки. Який код магнітола отримує для кожної назви, вирішує протокол
магнітоли: див. [Зіставте кнопки з магнітолою](radio-mapping.md).

### Поворотні ручки: таблиця `knobs` {#rotary-knobs-the-knobs-table}

Ручка — це 8-бітний лічильник в одному байті кадру:

```cpp
{canId, byteIndex, onIncrease, onDecrease}
```

Крок лічильника +1 — це одне клацання `onIncrease`, -1 — одне клацання `onDecrease`. За кадр
повідомляється не більше 4 клацань, і використовується не більше 4 рядків ручок. Перший кадр лише
задає початкове значення. Якщо ваша ручка лічить униз, коли ви крутите її «вперед», поміняйте дві
назви місцями, як це робить еталонний профіль для кадру `21F`.

## Крок 4: зберіть його {#step-4-build-it}

Ваш профіль вибирається трьома прапорцями збірки, без редагування будь-чого в `src/`. Файл
`firmware/platformio_override.sample.ini` уже має середовище для профілю з назвою `mine`:

1. Скопіюйте `firmware/platformio_override.sample.ini` у `firmware/platformio_override.ini`. Новий
   файл Git не відстежує; `platformio.ini` завантажує його автоматично.
2. Якщо ваш профіль називається не `mine`, змініть розділ `listen_mycar`, щоб він виглядав так,
   з вашою назвою замість `<name>` і `<Name>`:

    ```ini
    [env:listen_mycar]
    extends = env:listen_wifi
    lib_deps = car_<name>
    build_flags =
        ${env:listen_wifi.build_flags}
        -DCAR_PROFILE=CUSTOM
        '-DCAR_PROFILE_CUSTOM_HEADER="profile_<name>.h"'
        -DCAR_PROFILE_CUSTOM_OBJECT=kCar<Name>
    ```

    `lib_deps` потрібен: PlatformIO не відстежує `#include`, що приходить через макрос. Розділ
    `listen_mine` у тому самому файлі стосується вашої власної плати, а не автомобіля; залиште
    його.
3. Зберіть, з теки `firmware`:

    ```bash
    uvx platformio run -e listen_mycar
    ```

    Очікуваний результат: збирання закінчується на `SUCCESS`, а список залежностей угорі показує
    `|-- car_mine @ 1.0.0`. Інші повідомлення: див. [Типові помилки](#common-mistakes).
4. Прошийте й відкрийте консоль:

    ```bash
    uvx platformio run -e listen_mycar -t upload
    uvx platformio device monitor
    ```

    Очікуваний результат: `# profile: car=mine radio=xp` під час старту. Порт і режим
    завантажувача: [Прошивка](../quick-start/flash.md).

`listen_mycar` — це збірка лише прослуховування в паралельному режимі (поруч з адаптером):
вона декодує ваш автомобіль, подає сигнали парктроніків з динаміка пристрою і виводить рядки
консолі, але нічого не надсилає магнітолі й тримає виходи 12 V вимкненими. У консолі введіть
`keys`, щоб виводити кожну подію кнопки, `dump` — щоб виводити кожен кадр CAN.

### Режим декодера з вашим профілем {#decoder-mode-with-your-profile}

Щоб керувати магнітолою (кадри UART, ACC, виходи підсвічування й задньої передачі), додайте другий
розділ у свій `platformio_override.ini`. Цей розділ успішно зібрався під час проходження посібника:

```ini
[env:decoder_mycar]
extends = env:decoder_wifi
lib_deps = car_mine
build_flags =
    ${env:decoder_wifi.build_flags}
    -DCAR_PROFILE=CUSTOM
    '-DCAR_PROFILE_CUSTOM_HEADER="profile_mine.h"'
    -DCAR_PROFILE_CUSTOM_OBJECT=kCarMine
```

> [!CAUTION]
> **Режим декодера керує магнітолою і виходами 12 V**
>
> Прошивайте збірку декодера лише після того, як профіль пройшов тест на ПК і на стенді, і лише
> тоді, коли CAN-адаптер від'єднано: два передавачі на одній лінії UART і два джерела
> ACC означають виходи, що працюють один проти одного. Спершу прочитайте
> [Підключення магнітоли](../../en/install-in-car/radio-connection.md) і
> [Перша поїздка](../../en/install-in-car/first-drive.md). На шині CAN автомобіля ця збірка все одно
> лише слухає.

### Що навмисно не збирається {#what-does-not-build-on-purpose}

| Спроба | Результат |
|---|---|
| `decoder_tx_wifi` з `-DCAR_PROFILE=CUSTOM` | `#error "CAN transmit is not allowed with CAR_PROFILE=CUSTOM ..."` (перевірено під час проходження посібника) |
| `decoder_tx_wifi` з `-DCAR_PROFILE=GENERIC` | `#error "CAN transmit is not allowed with CAR_PROFILE=GENERIC ..."` (перевіряє `tools/check_tx_profile_lock.sh`) |
| `-DCAR_PROFILE=EXAMPLE` у будь-якому середовищі | `#error "CAR_PROFILE=EXAMPLE is a template for the host tests only ..."` |
| `CUSTOM` без прапорця заголовка чи об'єкта | `#error "CAR_PROFILE=CUSTOM needs ..."` |

## Не починайте з еталонного профілю {#do-not-start-from-the-reference-profile}

Можна було б скопіювати `firmware/lib/car_psa_aee2010/` замість шаблону. Знайте, що тоді
станеться: якщо ваш профіль зберігає еталонні функції, він декодує ідентифікатори кадрів еталонного
автомобіля (двері, налаштування, бортовий комп'ютер, клімат). Якщо він зберігає ще й
`psa::decodeBodyState` для запалювання, прошивка вважатиме ваш автомобіль автомобілем PSA AEE2010
і під час зміни налаштувань, і в умовах передачі (`firmware/lib/app/decoder.cpp`, `Decoder::begin`). Це правильно лише для автомобіля, для якого
вимірюванням підтверджено, що він використовує ті самі кадри. Вважайте кожен кадр іншого автомобіля **не
перевіреним** (unverified), доки ви його не записали, навіть для близького родича еталонного
автомобіля.

## Типові помилки {#common-mistakes}

| Симптом | Причина |
|---|---|
| `fatal error: profile_mine.h: No such file or directory` | `name` у `library.json` не змінено або бракує `lib_deps` |
| `# can=FAIL` під час старту, червоний світлодіод | `canBitrate` не є однією з шести підтримуваних швидкостей |
| кнопка повідомляється як утримувана весь час | її шаблон `mask` / `value` присутній у стані спокою |
| кнопки не на тому біті | `byteIndex` порахований від 1 замість 0 |
| вихід підсвічування вимикається через 1 s | кадр фар не повторюється хоча б раз на секунду |
| немає звукового сигналу, хоча зони змінюються | статус сторони не `4` (`PARK_ACTIVE`) |

Далі: [Перевірте свій профіль](test-your-profile.md).
