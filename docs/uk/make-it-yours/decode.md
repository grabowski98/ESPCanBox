# Декодуйте кадри

> [!NOTE]
> **Машинний переклад, потребує перевірки**
>
> Цю сторінку перекладено автоматично. Обов'язковим є англійський текст. Як надіслати
> виправлення: [Переклади](../../en/contributing/translations.md#send-your-work).

У вас є запис з маркерами ([Запишіть шину](record.md)). Тепер ви шукаєте біти, що змінилися, коли
ви щось робили в автомобілі. Ця сторінка робить це крок за кроком на справжніх записах еталонного
автомобіля, інструментом `firmware/tools/can_diff.py`.

Інструмент лише читає файли. Йому потрібен Python 3 і нічого більше. Усі команди нижче
запускаються з теки репозиторію.

Приклади використовують записи з репозиторію. Ваш власний запис із `record.py` лежить у теці
`logs` поруч із текою репозиторію, у файлі, назва якого закінчується на
`_can_YYYYMMDD_HHMMSS.log`. Вкажіть замість прикладу шлях до нього, наприклад
`python -I firmware/tools/can_diff.py ../logs/<назва файлу> --list`.

## Байти й біти {#bytes-and-bits}

Кадр CAN має ідентифікатор (три шістнадцяткові цифри, наприклад `0F6`) і до 8 байтів даних. Цей
проєкт нумерує їх так:

- байти від **1**: байт 1 — перший байт даних (`data[0]` у коді C++);
- біти **7..0** усередині байта, біт 0 — наймолодший;
- коротка форма `byte.bit`: `8.7` = байт 8, біт 7.

Приклад: кадр `0F6#884D1E2182585828` має байт 1 = `88`, байт 2 = `4D`, ... байт 8 = `28`.

Щоб побачити біти, запишіть кожну шістнадцяткову цифру як чотири двійкові:

| Hex | Двійкове (біти 7..0) |
|---|---|
| `24` | `0010 0100` |
| `A4` | `1010 0100` |

`24` і `A4` відрізняються лише крайнім лівим бітом, тож змінився біт 7.

## Що робить інструмент {#what-the-tool-does}

Для кожного маркера `can_diff.py` порівнює два часові вікна:

- **до**: секунди безпосередньо перед маркером (типово 3 s, `--before`);
- **після**: секунди безпосередньо після нього (типово 5 s, `--after`).

Він перелічує кожен біт, який був сталим у вікні «до» і змінився у вікні «після». Два фільтри
прибирають більшість шуму:

- **лічильники**: байт або півбайт, що в майже кожному кадрі всього запису змінюється на ту саму
  величину (лічильники, що циклічно зростають, таймери). Інструмент виводить їх один раз угорі й
  ніколи не повідомляє про них.
- **фон**: біт, що вже змінювався у вікні «до», для цього маркера ігнорується («ignored: N
  background bits» у виводі).

Він також перелічує ідентифікатори, що з'являються лише після маркера («new IDs»), і ті, що
зникають.

Спершу перевірте, що інструмент працює на вашому комп'ютері. Синтетичний файл — це вигаданий
автомобіль з відомими відповідями:

```
python -I firmware/tools/can_diff.py firmware/test_data/synthetic/marker_demo.log --selftest
```

```
selftest: 6 markers, 3216 frames, 0 errors
```

Корисні параметри:

| Параметр | Що він робить |
|---|---|
| `--list` | перелічує маркери з номерами й часом, потім зупиняється |
| `--marker N` | лише маркер N (можна повторювати) |
| `--match TEXT` | лише маркери, текст яких містить TEXT |
| `--after S`, `--before S` | довжина вікон у секундах |
| `--id 0F6,21F` | лише ці ідентифікатори |
| `--summary` | для вибраних маркерів: при скількох із них змінився кожен біт |
| `--export OUT` | записує в OUT лише рядки CAN, для інших програм |

Маркери — це рядки коментарів, що починаються з `# STEP`, `# MARK`, `# MARKER` або `# KROK`
(польське слово, використане в еталонних записах). Інший шаблон задається через `--marker-regex`.

## Приклад 1: задня передача (`0F6`) {#example-1-reverse-gear-0f6}

Крок 17 цього запису польською каже «задня передача: увімкнути на 3 s, вимкнути, 3 рази (без
перешкоди)». Крок тривав близько 27 s, тож візьміть довге вікно «після»:

```
python -I firmware/tools/can_diff.py firmware/test_data/captures/can_20261110_190421.log --marker 17 --after 25
```

Без `--id` інструмент перелічує 13 ідентифікаторів: `0A1 0B6 0E1 0E6 0F6 10B 128 161 227 236 2AD 3E7 3F6`.
Кадр парктроніків `0E1` теж змінюється, а повільні величини за 25 s плавно змінюються. Шукайте біт, що
змінюється **стільки разів, скільки ви виконали дію**. Тут він у `0F6`:

```
python -I firmware/tools/can_diff.py firmware/test_data/captures/can_20261110_190421.log --marker 17 --after 25 --id 0F6
```

```
==============================================================================
marker 17, line 43732, at 597.094 s
  # KROK 17 19:08:20.249 Wsteczny: wlacz 3 s, wylacz, 3 razy (bez przeszkody)
  window: 3.0 s before, 25.0 s after; ignored: 0 background bits, counters in 0 IDs
  0F6
    byte 2: 51 52
      bits: 2.1 0->1 x1 @+23.87s, 2.0 1->0 x1 @+23.87s
    byte 8: 24 A4 24 A4 24 A4 24 A4
      bits: 8.7 0->1 x7 @+8.67s
```

Як це читати:

- `byte 8: 24 A4 24 ...` — послідовність значень, яких набував байт, без повторів;
- `8.7 0->1 x7 @+8.67s`: біт 8.7 перед маркером був 0, змінився 7 разів, уперше через 8.67 s після
  маркера.

Біт 8.7 знову і знову ставав 1 і повертався, у такт із дією. Байт 2 змінився один раз, ближче до
кінця: це не дія.

План казав тричі; у вікні біт ставав 1 чотири рази. Запис не пояснює чому. Довіряйте тому, що
показує файл, звіряйте з нотатками і підтверджуйте сигнал на другому записі.

Результат: задня передача = `0F6` 8.7 (виміряно (measured): `can_20261110_190421.log`, крок 17; той
самий біт є у `vehicles/peugeot-508-sw-2015/508.dbc`).

## Приклад 2: запалювання і двигун (`0F6` байт 1) {#example-2-ignition-and-engine-0f6-byte-1}

Деякі сигнали — не один біт, а цілий байт з кількома значеннями. Крок 3 каже «запустити двигун,
10 s без руху»:

```
python -I firmware/tools/can_diff.py firmware/test_data/captures/can_20261110_190421.log --marker 3 --after 10 --id 0F6
```

```
==============================================================================
marker 3, line 4078, at 416.094 s
  # KROK 3 19:05:19.255 Odpal silnik, 10 s bez ruchu
  window: 3.0 s before, 10.0 s after; ignored: 0 background bits, counters in 0 IDs
  0F6
    byte 1: 88 90 91 89 8A 8E
      bits: 1.4 0->1 x2 @+3.30s, 1.3 1->0 x2 @+3.30s, 1.2 0->1 x1 @+5.02s, 1.1 0->1 x1 @+4.03s, 1.0 0->1 x2 @+3.46s
    byte 8: 20 24 64
      bits: 8.6 0->1 x1 @+6.12s, 8.2 0->1 x1 @+4.07s
```

Тут список бітів заплутаний, але картину показують **значення байта**: `88` до, потім
`90 91 89 8A`, поки крутить стартер, потім `8E`, коли двигун працює. З більшою кількістю записів
вимкнення й увімкнення запалювання та запуску двигуна еталонний автомобіль дає `80` вимкнено, `88`
увімкнено, `90`/`91`/`89`/`8A` прокручування стартером, `8E` двигун працює, `86`/`84` вимикання
(виміряно: записи з кроками запалювання і двигуна, `508.dbc`).

Байт 8 теж змінився (`20 24 64`). Що означають ці два біти, невідомо. Не приписуйте біту значення
лише тому, що він змінився в той самий час.

Для першого ввімкнення немає вікна «до»: шина спала, і кожен ідентифікатор біля маркера «новий»
(див. [Запис](record.md#how-markers-get-their-time)). Тоді читайте перші кадри напряму. Перший кадр
`0F6` цього запису:

```
(398.212947) can0 0F6#884D1E2182585828
```

Байт 1 = `88`: запалювання ввімкнено.

## Приклад 3: кнопка на кермі (`21F`) {#example-3-a-steering-wheel-button-21f}

Чистий випадок. Крок 3 у `can_20261111_190817.log` каже «кермо: гучніше тричі, кожні 2 s». Цього
разу без `--id`:

```
python -I firmware/tools/can_diff.py firmware/test_data/captures/can_20261111_190817.log --marker 3 --after 4.5
```

```
firmware/test_data/captures/can_20261111_190817.log: 30040 frames, 62 IDs, 14 markers, 0 broken lines skipped
counters (never reported): 0E6:8H,8L 10B:5L 236:5 3F6:3H
==============================================================================
marker 3, line 6809, at 223.999 s
  # KROK 3 19:08:54.163 Kierownica: glosnosc + trzy razy, co 2 s
  window: 3.0 s before, 4.5 s after; ignored: 10 background bits, counters in 4 IDs
  21F
    byte 1: 00 08 00 08 00
      bits: 1.3 0->1 x4 @+0.78s
  new IDs (absent before, present after): 1A5(4)
```

Один біт: `21F` 1.3 (байт 1 = `08`, поки кнопку натиснуто). Вікно 4.5 s вміщує два з трьох
натискань: 4 зміни. Наступний маркер іде через 4.5 s, тож довше вікно захопило б наступний крок.

Новий ідентифікатор `1A5` не від кнопки. У цьому записі було підключено сторонній
CAN-адаптер, і він надсилає `1A5` (рівень гучності) за кілька мілісекунд після того, як магнітола
змінює гучність (виміряно: [Peugeot 508 SW](../../en/reference/vehicles/peugeot-508.md)). Інші
пристрої на шині теж реагують на вашу дію. Якщо можете, зробіть один запис без них.

Результат: гучніше = `21F` 1.3 (виміряно: `can_20261111_190817.log` і `can_20261111_191045.log`
разом з лінією UART до магнітоли).

## Приклад 4: парктроніки (`0E1`) {#example-4-parking-sensors-0e1}

Кадр, повний полів. Крок 18 у `can_20261111_191045.log` каже «задні датчики: задню передачу
ввімкнено, наближайте предмет до заднього бампера, доки не з'явиться безперервний сигнал, заберіть
його, вимкніть задню передачу». Цей файл починається з кроку 13, тож крок 18 — це маркер 6
(перевірте через `--list`):

Коли багато сусідніх бітів змінюються разом, це одне поле. Розбийте байти на групи бітів, що
рухаються разом:

| Поле | Де | Що тут роблять значення | Значення на еталонному автомобілі |
|---|---|---|---|
| стан ззаду, стан спереду | байт 1, біти 7-5 і 4-2 | `90` = `100 100 00`: ззаду 4, спереду 4 | 4 активний, 5 очікування (виміряно) |
| запит звуку | 2.4 | 1, поки автомобіль подає сигнал | виміряно |
| сторони | 2.7-2.6 | `D0`: обидві сторони | виміряно |
| інтервал сигналів | байт 3, біти 5-0 | `3F`, потім значення спадають, коли предмет наближається | `3F` без звуку, `39` ... `0B` сигнали, `00` безперервний сигнал (виміряно) |
| зони датчиків | байти 4-6, по 3 біти | значення спадають, коли предмет наближається | 0 найближче ... 7 далеко (виміряно) |

Значення: `vehicles/peugeot-508-sw-2015/508.dbc` та
[Peugeot 508 SW](../../en/reference/vehicles/peugeot-508.md#parking-sensors-0e1).

Біт 1.5 теж змінився (`B4` на `90`), але його немає в списку: він уже рухався у вікні «до», яке
перекриває кінець кроку із задньою передачею. Фільтр фону може сховати справжній біт. Якщо ви
чекаєте біт і не бачите його, посуньте вікно: з `--before 1` цей запуск показує й `1.5 1->0 x2`.
Значення байтів (`B0 B4 90 B0`) завжди показуються повністю.

## Повторіть дію, порахуйте збіги {#repeat-the-action-count-the-hits}

Найкращий доказ — біт, що змінюється при **кожному** маркері тієї самої дії і ні при якому іншому.
З одним маркером на повторення `--match` і `--summary` порахують це за вас. На синтетичному файлі
(вигаданий автомобіль, три відчинення дверей і три натискання кнопки):

```
python -I firmware/tools/can_diff.py firmware/test_data/synthetic/marker_demo.log --match door --summary
```

```
firmware/test_data/synthetic/marker_demo.log: 3216 frames, 5 IDs, 6 markers, 4 broken lines skipped
counters (never reported): 100:2,8L
==============================================================================
summary of 3 markers: 1 3 5
  3/3  300 2.5
```

`3/3  300 2.5` = у кадрі `300` біт 2.5 (байт 2, біт 5) змінився при всіх трьох маркерах
дверей. З `--match volume` відповідь —
`3/3  310 1.3`. 4 пошкоджені рядки зроблено навмисно: інструмент пропускає рядки, що схожі на
кадри, але пошкоджені (непарна кількість шістнадцяткових цифр, більше 8 байтів, 4-значний
ідентифікатор).

## Як часто приходить кадр {#how-often-a-frame-comes}

Деяким сигналам потрібен кадр, що повторюється досить часто (див.
[Контрольний список перенесення](porting-checklist.md)). Інструмент період не показує. Визначте
його з файлу:

1. Відкрийте запис у текстовому редакторі.
2. Знайдіть `can0 0F6#` (замість `0F6` підставте свій ID).
3. Відніміть час двох сусідніх рядків. У `can_20261111_191045.log`:
   336.199989 - 335.699989 = 0,5 s.
4. Перевірте кілька пар. Кадр, який надсилається лише при зміні, має довгі нерівні проміжки.

У Git Bash `grep "can0 0F6#" <файл> | head -5` виводить перші п'ять рядків одного ID.

## Від бітів до значень {#from-bits-to-values}

Поле стає числом через **масштаб** (scale) і **зсув** (offset):

```
value = raw × scale + offset
```

Приклад з еталонного автомобіля: зовнішня температура = `0F6` байт 7, масштаб 0.5, зсув -40, тобто
`value / 2 - 40` °C (виміряно: збігається з температурою, яку CAN-адаптер надсилав магнітолі, у 21
з 21 кадру, `can_20261111_191045.log`). У кадрі `0F6#884D1E2182585828` вище байт 7 = `58` = 88, і
88 / 2 - 40 = 4 °C.

Щоб знайти масштаб, запишіть значення у двох відомих точках (наприклад температуру, показану на
приладовій панелі, або гучність магнітоли) і порівняйте.

### Запишіть це у файл DBC {#write-it-into-a-dbc-file}

Файл DBC — це текстовий файл, що перелічує кадри й сигнали. Його читає багато інструментів CAN.
Файл еталонного автомобіля — `vehicles/peugeot-508-sw-2015/508.dbc`. Один рядок на сигнал:

```
BO_ 246 BODY_STATE: 8 CAR
 SG_ reverse : 63|1@0+ (1,0) [0|1] "" DEVICE
```

- `246` — ідентифікатор у десятковому вигляді (`0F6` hex = 246).
- `63|1@0+`: початковий біт 63, довжина 1 біт, `@0` = порядок байтів big-endian (його ще називають
  Motorola; вибирайте його в SavvyCAN або cantools), `+` = без знака.
  З `@0` початковий біт = (байт - 1) × 8 + біт для найстаршого біта поля: байт 8 біт 7 =
  7 × 8 + 7 = 63. Інтервал сигналів, байт 3 біти 5-0, — це `21|6@0+`.
- `(1,0)` = масштаб і зсув; зовнішня температура має `(0.5,-40)`.

Дайте кожному сигналу коментар, що починається з його статусу (`measured: ...` із записом або
`unverified: ...` з джерелом), як у `508.dbc`. Потім перетворіть сигнали на профіль автомобіля:
[Напишіть профіль автомобіля](write-a-profile.md).

## SavvyCAN та інші інструменти {#savvycan-and-other-tools}

SavvyCAN — безкоштовна настільна програма для аналізу CAN, що читає файли DBC і файли журналів у
кількох форматах. Цей проєкт **не має живого зв'язку** з нею: у прошивці немає GVRET чи подібного
протоколу. Ви працюєте із записаними файлами. Чи відкриває ваша версія SavvyCAN формат записів
цього проєкту напряму, не перевіряли; якщо вона відкидає рядки коментарів або `uartA`, спершу
експортуйте рядки CAN:

```
python -I firmware/tools/can_diff.py my_recording.log --export frames_only.log
```

## Обмеження інструмента {#limits-of-the-tool}

- Маркер не має власного часу: він отримує час наступного кадру CAN. На сплячій шині це момент,
  коли шина прокидається.
- Сигнал, що змінюється повільно (температура, паливо), може не змінитися всередині вікна.
- Біт, що вже рухався перед маркером, ховається (див. приклад 4).
- Фільтр лічильників шукає рівномірні кроки. Лічильник, що стрибає, або контрольна сума не
  розпізнаються і з'являються як активний біт у кожному вікні.
- Читаються лише 11-бітні ідентифікатори (три шістнадцяткові цифри).

Що залишається невідомим після декодування: що автомобіль робить зі значенням, зміни якого ви не бачили.
Знайдений сигнал виміряно для тих дій, які ви записали, і не більше.
