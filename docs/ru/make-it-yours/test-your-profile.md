# Проверьте свой профиль

> [!NOTE]
> **Машинный перевод, требует проверки**
>
> Эта страница переведена автоматически. Обязательным является английский текст. Как прислать
> исправление перевода: [Переводы](../../en/contributing/translations.md#send-your-work).

Прежде чем профиль окажется рядом с автомобилем, запустите его на ПК. **Хост-тест** (host test)
подаёт запись кадр за кадром в тот же код декодера, что работает на устройстве, и выводит, что
сделало бы устройство: строки консоли, кадры для магнитолы и каждое изменение выходов 12 В и
зуммера. Вы один раз читаете этот вывод, сверяете его с тем, что делали в автомобиле, и сохраняете
как эталон. С этого момента тест сообщает вам, когда изменение что-то ломает.

Ничего не прошивается и никакой порт не открывается. Не нужны ни плата, ни автомобиль.

Эта страница продолжает руководство со страницы [Напишите профиль автомобиля](write-a-profile.md) с
выдуманным профилем `mine`. Каждая команда выполнена на копии репозитория. Все команды
выполняются из папки `firmware`, в Git Bash.

> [!TIP]
> **Сначала пробный прогон**
>
> Прежде чем вписывать в `car_mine` свои кадры, можно проверить копию и переименования.
> Выполните шаги 2–4 со значениями шаблона, которые ещё остались в `car_mine`, и с
> `run_file mine_car test_host/synthetic/example_car.log` в шаге 3. Вывод должен
> заканчиваться строками `example profile works on every axis` и `### code=0`. Затем измените
> профиль под свой автомобиль и впишите свою запись в строку `run_file`.

## Что понадобится {#what-you-need}

- Git Bash в Windows или оболочка в Linux или macOS;
- `uv`: через него тестовый скрипт получает компилятор C++ (пакет `ziglang`; первый запуск его
  скачивает, поэтому один раз нужен интернет), либо задайте свой через
  `CXX=g++`. Подробности: [Хост-тесты](../../en/testing/host-tests.md);
- ваш профиль в `firmware/lib/car_<name>/`;
- запись вашего автомобиля с маркерами ([Запись шины](record.md)), очищенная
  `python -I ../tools/sanitize_capture.py`, если вы будете ею делиться ([Поделитесь своим автомобилем](contribute.md)).

## Шаг 1: положите запись на место {#step-1-put-the-recording-in-place}

| Запись | Куда |
|---|---|
| настоящая запись вашего автомобиля | `firmware/test_data/captures/`, с одной строкой в его `README.md` (что, как записано, какой тест её использует) |
| кадры, написанные вручную, чтобы проверить случай | `firmware/test_host/synthetic/`, с комментарием вверху, что кадры выдуманы |

Формат обычный, `(seconds) can0 ID#DATA`. Строки, которые не являются кадрами CAN (комментарии,
строки UART), тест пропускает. Написанные вручную файлы для тестов профиля кладите в
`test_host/synthetic/`, а не в `test_data/synthetic/`: та папка для `can_diff.py`.

Файл, написанный вручную, — хорошее начало, потому что вы точно знаете, что должно произойти. Файл,
использованный в руководстве, `test_host/synthetic/mine_car.log`, начинался так (учебный автомобиль
со страницы [Напишите профиль](write-a-profile.md); этого файла нет в репозитории, поэтому напишите
свой):

```text
# Invented frames for the "mine" profile (tutorial). Not a real car.
# 2C0 = ignition / reverse, 1F0 = buttons + knob, 350 = rear parking, 2C8 = lights
(0.000000) can0 2C0#00000000
(0.200000) can0 2C0#00010000
(0.400000) can0 2C0#00020000
(0.600000) can0 1F0#01000000
(0.700000) can0 1F0#01000000
```

## Шаг 2: скопируйте пример теста {#step-2-copy-the-example-test}

У профиля-шаблона есть свой тест, `firmware/test_host/example_car.cpp`. Скопируйте его, из папки
`firmware`:

```bash
cp test_host/example_car.cpp test_host/mine_car.cpp
```

Затем измените в `mine_car.cpp` четыре вещи:

1. `#include "profile_example.h"` становится `#include "profile_mine.h"`;
2. каждый `kCarExample` становится `kCarMine` (шесть раз, в четырёх строках; проще всего поиском с
   заменой);
3. текст подсказки `example_car <capture.log>` становится `mine_car <capture.log>` (в комментарии
   вверху и в строке `fprintf`);
4. последняя проверка, строка, которая начинается с `const bool ok =`. Она требует, чтобы
   **каждый** выход что-то сделал. Части: `r.accMs` = ACC, `r.illMs` = фары, `r.revMs` = задний
   ход, `r.toneMs` = зуммер, `r.uartFrames` = кадры для магнитолы, `d.haveLastKey()` = хотя бы
   одна кнопка. Уберите части, которых нет в вашем профиле. Профиль без парктроников не проходит
   на `r.toneMs > 0`, и тогда тест завершается с кодом выхода 1. Готовые строки:
    - только зажигание и кнопки:
      `const bool ok = r.accMs > 0 && r.uartFrames > 0 && d.haveLastKey();`
    - только зажигание: `const bool ok = r.accMs > 0;`

    Текст `example profile works on every axis` можно оставить: это только подпись.

## Шаг 3: добавьте тест в тестовый скрипт {#step-3-add-the-test-to-the-test-script}

Откройте `firmware/tools/run_host_tests.sh` и найдите блок, который заканчивается на
`finish example_car`. Добавьте свой тест сразу после него:

```bash
# My car profile
# shellcheck disable=SC2086
build mine_car $S38_LIBS profile_mine.cpp
rm -f "$OUT/mine_car.actual.txt"
run_file mine_car test_host/synthetic/mine_car.log
finish mine_car
```

`build` компилирует ваш тест вместе с декодером, его библиотеками и файлом вашего профиля.
`$S38_LIBS` — список файлов декодера, нужных тесту; оставьте его как есть. `run_file` запускает его на указанном файле, с путём относительно `firmware/`. Для записи
в `test_data/captures/` укажите этот путь.

## Шаг 4: первый запуск, прочитайте вывод, сохраните эталон {#step-4-first-run-read-the-output-store-the-reference}

Запустите все хост-тесты (`cd firmware` нужен, только если вы в папке репозитория):

```bash
cd firmware
bash tools/run_host_tests.sh
```

Ожидаемый результат: все существующие тесты выводят `OK`. Ваш останавливает скрипт, потому что у него ещё нет эталона:

```text
OK     example_car
FAIL   mine_car: no reference test_host/expected/mine_car.txt
```

Вывод теперь лежит в `firmware/.build_host/mine_car.actual.txt`. **Прочитайте его** и сравните с
тем, что вы делали в автомобиле (или написали в файле). Это и есть настоящая проверка; сохранённый
файл только повторяет её потом. Фрагмент из прохождения руководства:

```text
### mine_car test_host/synthetic/mine_car.log
profile mine: 500000 bit/s, 4 key rows, 1 knob(s), txAllow 0
     0 outputs acc=0 ill=0 rev=0 tone=0 continuous=0
console [car] acc=1
   200 radio 2E EA 02 01 0A 08
   200 outputs acc=1 ill=0 rev=0 tone=0 continuous=0
console [key] code=14 state=1
   600 radio 2E 20 02 14 01 C8
console [key] code=14 state=2
   800 radio 2E 20 02 14 02 C7
...
console [park] rear=4 front=0 sound=1 rear interval=0x00 zones rear 707 front 777
  1600 radio 2E 32 07 02 05 00 05 05 05 05 AB
  1600 outputs acc=1 ill=1 rev=1 tone=1 continuous=1
...
frames=21 uart_bytes=106 uart_frames=13 acc_ms=3101 ill_ms=1001 rev_ms=800 tone_ms=390 keys_dropped=0
example profile works on every axis
### code=0
```

Как это читать:

| Строка | Смысл |
|---|---|
| `profile mine: ...` | что содержит ваш профиль: скорость, число строк кнопок и ручек, список передачи (для собственного профиля всегда 0) |
| `console ...` | строка, которую устройство вывело бы в консоль USB |
| `200 radio 2E EA ...` | кадр для магнитолы на 200 мс (время по часам записи). `EA` = питание включено, `20` = кнопка, `32` = парктроники, `3E` = флаг препятствия. См. [Протокол XP](../../en/reference/xp-protocol.md) |
| `outputs acc=1 ill=0 rev=0 tone=0 continuous=0` | изменение выходов 12 В (ACC, подсветка, задний ход) или зуммера |
| `[key] code=14 state=1` | кнопка с кодом магнитолы `14` (громкость +): 1 нажата, 2 удерживается, 0 отпущена |
| последние строки | итоги в миллисекундах и ваша проверка `ok` |

Что стоит проверить в своём выводе:

- ACC включается с вашим кадром «зажигание включено» и выключается через 2,5 с после выключения
  зажигания. Во фрагменте он не выключается никогда, потому что воспроизведение заканчивается
  через 1 с после последнего кадра.
- Выход подсветки выключается через 1 с после последнего кадра фар (при прохождении руководства:
  кадр фар на 1100 мс, `ill=0` на 2101 мс). Если ваш автомобиль повторяет кадр фар, этого не
  происходит.
- Каждая кнопка даёт `state=1`, затем `state=2` каждые 200 мс, пока её держат, затем `state=0`.
- Сигнал начинается с первой зоны ниже 7 и становится непрерывным только с интервалом `0x00`.
- Кнопка показывает не тот код, что вы ожидаете: см. [Сопоставление с магнитолой](radio-mapping.md).
  Переназначения по умолчанию берутся из профиля автомобиля; в примере профиля их нет, поэтому
  пример теста показывает SRC как `code=21 state=1`, отправленный без изменений.

> [!WARNING]
> **Сохранённый `### code=1` проходит как OK**
>
> Скрипт только сравнивает вывод с сохранённым файлом. На сохранённом `### code=1` он не
> останавливается. Проверьте последние строки (пункт 1 ниже) до копирования, иначе тест
> пройдёт, хотя он не удался.

Когда вывод правильный, сохраните его как эталон:

1. Проверьте две последние строки `.build_host/mine_car.actual.txt`. Это должны быть
   `example profile works on every axis` и `### code=0`.
2. Если видите `FAIL: an axis of the example profile did nothing` и `### code=1`, исправьте
   строку `const bool ok =` (шаг 2, пункт 4) и запустите скрипт снова.
3. Скопируйте файл и запустите скрипт снова:

```bash
cp .build_host/mine_car.actual.txt test_host/expected/mine_car.txt
bash tools/run_host_tests.sh
```

Ожидаемый результат: `OK     mine_car` и `All tests match the references.`

> [!WARNING]
> **Не используйте для этого `--record-golden`**
>
> `bash tools/run_host_tests.sh --record-golden` заново записывает эталоны **всех** тестов,
> включая контрольные файлы (golden files) эталонного автомобиля. Используйте его, только когда вы
> намеренно изменили поведение и проверили каждое отличие. Для одного нового теста скопируйте его
> файл, как показано выше.

## Быстрый цикл для одного теста {#a-faster-loop-for-one-test}

Полный скрипт при прохождении руководства занял от 30 до 50 секунд. Пока вы работаете над профилем,
можно компилировать и запускать только свой тест. Сначала один раз запустите полный тестовый
скрипт: он скачивает компилятор в кэш `uv`, а команда ниже использует этот кэш (`--offline`). Из
папки `firmware`, в Git Bash:

```bash
LIBS="vehicle_settings.cpp radio_commands.cpp can_tx_gate.cpp settings_changer.cpp car_state.cpp decoder.cpp candump.cpp psa_frames.cpp xp_protocol.cpp xp_keys.cpp xp_keys_custom.cpp xp_parking.cpp xp_car.cpp psa_signals.cpp xp_signals.cpp radio_session.cpp power_policy.cpp parking_beeper.cpp xp_settings.cpp profile_psa_aee2010.cpp tx_allowlist.cpp protocol_xp.cpp profile_generic.cpp profile_mine.cpp vehicle_signals.cpp"
SRCS=""; for f in $LIBS; do SRCS="$SRCS $(ls lib/*/$f)"; done
INC=""; for d in lib/*/; do INC="$INC -I ${d%/}"; done
mkdir -p .build_host
uvx --offline --from ziglang python -I -m ziglang c++ -std=c++17 -O1 -Wall $INC -I include \
    test_host/mine_car.cpp $SRCS -o .build_host/mine_car.exe < /dev/null
./.build_host/mine_car.exe test_host/synthetic/mine_car.log
```

Список файлов тот же, что `$S38_LIBS` в тестовом скрипте, плюс ваш профиль и
`vehicle_signals.cpp`. Если список в скрипте изменится, скопируйте его оттуда. Прежде чем чем-то
делиться, запустите полный скрипт.

## Запустите и проверку слоёв {#also-run-the-layering-check}

```bash
python -I tools/check_layering.py
```

Она проверяет, что ваш профиль не включает ничего из протокола магнитолы, из `src/` или из
фреймворка Arduino и что ни одно имя заголовка не встречается дважды. При прохождении руководства
она перечислила `car_mine` среди библиотек и закончилась строкой `Layering OK.`

## Что этот тест не покрывает {#what-this-test-does-not-cover}

- Код в `firmware/src/` (драйвер CAN, UART, выходы 12 В, звук) на ПК не выполняется. Первая
  проверка настоящего железа — [проверка на стенде](../quick-start/bench-test.md).
- Временные характеристики на настоящей шине: воспроизведение идёт шагами по 1 мс и не теряет
  кадров.
- Правильна ли ваша расшифровка для автомобиля. Тест может показать только то, что ваш профиль
  делает из кадров. Поэтому вы читаете вывод, сверяя с маркерами, прежде чем сохранить его.

Далее: [Сопоставление с магнитолой](radio-mapping.md).
