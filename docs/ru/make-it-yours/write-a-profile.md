# Напишите профиль автомобиля

> [!NOTE]
> **Машинный перевод, требует проверки**
>
> Эта страница переведена автоматически. Обязательным является английский текст. Как прислать
> исправление перевода: [Переводы](../../en/contributing/translations.md#send-your-work).

**Профиль автомобиля** говорит прошивке, как читать один автомобиль: скорость шины, какие биты
отвечают за кнопки на руле, где зажигание, задний ход, фары и парктроники. Это одна константная
структура на C++ (`vehicle::CarProfile`, определена в `firmware/lib/core/car_profile.h`),
вкомпилированная в программу. Профиль выбирается при сборке прошивки; пока устройство работает,
его нельзя сменить.

Эта страница ведёт вас от расшифрованных кадров к профилю, который собирается. Следующая страница,
[Проверьте свой профиль](test-your-profile.md), проверяет его на записи на вашем ПК.

Каждый шаг этой страницы опробован на копии репозитория с выдуманным автомобилем. Там, где что-то
пошло не так, страница об этом говорит и показывает сообщение, которое вы увидите.

> [!CAUTION]
> **Ваш собственный профиль на шине автомобиля только слушает**
>
> Профиль, собранный с `-DCAR_PROFILE=CUSTOM`, никогда не может передавать в шину CAN автомобиля.
> Окружение с передачей `decoder_tx_wifi` с ним не собирается и останавливается с сообщением
> `CAN transmit is not allowed with CAR_PROFILE=CUSTOM (listen-only; add a named profile in src/config.h)`.
> Не пытайтесь это обойти. Передача для нового автомобиля требует измеренных кадров, проверок
> содержимого, написанных в коде, и тестов: см. [Передача в шину CAN](../../en/safety/transmit.md).

## Что покрывает профиль {#what-a-profile-covers}

Разберитесь в этом до начала работы. Профиль покрывает только часть того, что устройство делает на эталонном
автомобиле (Peugeot 508 SW 2015, профиль `psa_aee2010`).

| Функция | Через ваш профиль | Примечания |
|---|---|---|
| Скорость шины | да | `canBitrate` |
| Кнопки на руле и на панели, поворотные ручки | да | таблицы `keys` и `knobs` |
| Состояние зажигания и двигателя, задний ход | да | функция `decodeBody`; управляет ACC и выходом заднего хода |
| Фары включены | да | функция `decodeLights`; управляет выходом подсветки |
| Парктроники и звуковой сигнал из динамика устройства | да | функция `decodeParking` |
| Список разрешённых кадров | **нет**: поле остаётся пустым (`nullptr, 0`) | профиль `CUSTOM` не может передавать (см. выше) |
| Кадры, в которых есть VIN | указываются, для информации | `privacyIds`; прошивка его не использует |
| Двери, багажник и капот | да | функция `decodeDoors` -> `vehicle::DoorState` |
| Бортовой компьютер | да, с ограничением | функция `decodeTrip` -> `vehicle::TripData`. Значения сохраняют кодировку эталонного автомобиля (их смысл не проверен): заполняйте их, только если ваш автомобиль использует такую же |
| Наружная температура, экономичный режим | да | функции `decodeOutsideTemp`, `decodeEcoMode` |
| Состояние климат-контроля | да | функция `decodeClimate` -> `vehicle::ClimateState` |
| Угол поворота руля | да, с ограничением | функция `decodeSteering`; масштаб на эталонном автомобиле не проверен |
| Настройки автомобиля (то, что показывает магнитола) | да | функция `decodeSettings` -> `vehicle::VehicleSettings` (пункты с нейтральными идентификаторами) |
| Изменение настройки автомобиля с магнитолы | **нет** | только эталонный профиль `psa_aee2010`, за шлюзом передачи |

Данные автомобиля для экрана магнитолы (от дверей до настроек автомобиля) необязательны:
оставьте указатель `nullptr`, и магнитола никогда не получит эти данные. Каждая функция заполняет
нейтральный тип из `firmware/lib/core/vehicle_signals.h`; протокол магнитолы превращает его в свой
кадр. Их перечисляет подраздел «Данные автомобиля для экрана магнитолы» в шаге 3.

Поэтому с протоколом магнитолы XP профиль другого автомобиля даёт магнитоле: состояние питания
(ACC), нажатия кнопок, картинку парктроников, флаг препятствия и все функции данных автомобиля,
которые заполнил профиль. Изменение настроек автомобиля с магнитолы остаётся за эталонным
автомобилем.

## Перед началом {#before-you-start}

Вам понадобятся:

- скорость, провода CAN и тип шины вашего автомобиля ([Найдите свою шину](find-your-bus.md));
- запись с маркерами ([Запись шины](record.md));
- расшифрованные кадры и биты ([Расшифровка кадров](decode.md)). Запишите каждый со статусом,
  **измерено** (measured) или **не проверено** (unverified), в копию `vehicles/_template/README.md`;
- инструменты сборки со страницы [Прошивка](../quick-start/flash.md): `uv` и, в Windows, Git Bash.

Все сигналы не нужны. Профиль только с зажиганием уже полезен: он может переключать ACC
магнитолы. Не включайте ничего, что вы не измерили.

## Шаг 1: скопируйте шаблон {#step-1-copy-the-template}

Шаблон `firmware/lib/car_example/` описывает выдуманный автомобиль с комментариями к каждому полю.
Его компилируют только тесты на компьютере (хост-тесты), в прошивку он никогда не попадает.

> [!NOTE]
> **Два выдуманных автомобиля**
>
> Шаблон использует кадры `100`, `200`, `300` и `400`. Примеры на этой странице и на странице
> [Проверьте свой профиль](test-your-profile.md) взяты со **второго** выдуманного автомобиля,
> "учебного автомобиля" (кадры `2C0`, `1F0`, `350`, `2C8`), придуманного, когда эти страницы
> опробовались. Его записи в репозитории нет; фрагменты только показывают, как выглядят ваши
> собственные значения. В своей копии вы заменяете значения шаблона кадрами своего автомобиля.

Выберите короткое имя профиля строчными буквами, например `mine`. Затем откройте Git Bash в папке
`firmware`: в Проводнике откройте эту папку, щёлкните правой кнопкой мыши и выберите
«Open Git Bash here» (в Windows 11 в пункте «Показать дополнительные параметры»). Выполните:

```bash
cp -r lib/car_example lib/car_mine
cd lib/car_mine
mv profile_example.h profile_mine.h
mv profile_example.cpp profile_mine.cpp
cd ../..
```

Имена файлов должны быть уникальными во всём `firmware/lib/`: у всех библиотек один общий путь
включения, и `tools/check_layering.py` сообщает об имени заголовка, которое встречается дважды.

## Шаг 2: переименуйте внутри файлов {#step-2-rename-inside-the-files}

Откройте три файла в текстовом редакторе и переименуйте:

| Где | Было | Стало |
|---|---|---|
| `profile_mine.cpp`, первый `#include` | `"profile_example.h"` | `"profile_mine.h"` |
| оба файла | `kCarExample` | `kCarMine` |
| оба файла | `namespace example` и `example::` | `namespace mine` и `mine::` |
| `profile_mine.cpp`, первое поле профиля | `"example"` | `"mine"` |
| `library.json`, поле `name` | `"car_example"` | `"car_mine"` |
| `library.json`, поле `description` | текст шаблона | одна строка о вашем автомобиле |

> [!WARNING]
> **Не забудьте `library.json`**
>
> PlatformIO узнаёт библиотеку по полю `name` в `library.json`, а не по имени папки. Окружения
> `listen` игнорируют библиотеку с именем `car_example` (`lib_ignore` в
> `firmware/platformio.ini`). Со старым именем сборка падает с
> `Warning! Could not find the package with 'car_mine' requirements`, а затем
> `fatal error: profile_mine.h: No such file or directory`.

## Шаг 3: заполните профиль {#step-3-fill-in-the-profile}

Работайте в таком порядке:

1. В `profile_mine.h` задайте четыре ID кадров `ID_BODY`, `ID_KEYS`, `ID_PARKING` и
   `ID_LIGHTS` равными кадрам вашего автомобиля. ID, функцию которого вы зададите как `nullptr`
   (пункт 4), не читается.
2. В `profile_mine.cpp` перепишите функции `decodeBody`, `decodeParking` и `decodeLights`
   (разделы ниже).
3. В том же файле заполните таблицы `KEYS` и `KNOBS` (разделы ниже).
4. В конце файла заполните константу профиля (таблица ниже). У её полей в коде нет имён, важен
   только порядок, поэтому оставьте комментарий рядом с каждой строкой.

Хотите проверить копию и переименования, прежде чем менять какие-либо значения? Сначала сделайте
пробный прогон со страницы [Проверьте свой профиль](test-your-profile.md).

Поля константы профиля по порядку:

| Поле | Что туда записать |
|---|---|
| `id` | короткое имя в ASCII, показывается в консоли (`# profile: car=mine radio=xp`) и в панели |
| `canBitrate` | измеренная скорость в бит/с |
| `physicalLayer` | `vehicle::PhysicalLayer::UNKNOWN`, `HIGH_SPEED` или `LOW_SPEED_FT`. Только для информации: трансивер определяет плата. Оставьте `UNKNOWN`, пока не измерили |
| `keys`, `keyCount` | таблица кнопок (ниже); `nullptr, 0`, если кнопок нет |
| `knobs`, `knobCount` | таблица ручек (ниже); `nullptr, 0`, если ручек нет |
| `txAllow`, `txAllowCount` | `nullptr, 0`. Профиль `CUSTOM` никогда не передаёт |
| `privacyIds`, `privacyCount` | ID кадров, в которых в вашем автомобиле есть VIN, если вы их знаете; иначе `nullptr, 0` |
| `decodeParking` | ваша функция парктроников или `nullptr` |
| `decodeBody` | ваша функция зажигания и заднего хода или `nullptr` |
| `decodeLights` | ваша функция фар или `nullptr` |
| `powerOutputs` | `true` только тогда, когда `decodeBody` надёжно читает зажигание; `false` держит все выходы 12 В выключенными |
| `keyRemapDefaults`, `keyRemapDefaultCount` | `nullptr, 0`: каждая кнопка доходит до магнитолы со своим кодом. Строки `{from, to}` (коды XP) только для переназначений, которые нужны по умолчанию; см. [Сопоставление с магнитолой](radio-mapping.md#default-remappings-come-from-the-car-profile) |

`nullptr` допустим всегда: тогда этот сигнал никогда не формируется.

### Номера байтов в коде начинаются с 0 {#byte-numbers-in-code-start-at-0}

Документация и страницы автомобилей считают байты CAN с **1** (байт 1 = первый байт данных). В C++
первый байт — `f.data[0]`, и поле `byteIndex` в таблицах — тот же индекс. Поэтому кнопка, которую
вы записали как "байт 1, бит 2", — это `byteIndex 0, mask 0x04`. Проверьте это дважды: здесь проще
всего ошибиться.

### Скорость {#bit-rate}

`src/can_bus.cpp` знает такие скорости: 50000, 100000, 125000, 250000, 500000 и 1000000 бит/с.
Любое другое значение компилируется, но контроллер CAN не запускается: консоль показывает
`# can=FAIL`, светодиод состояния становится красным, а выходы 12 В остаются выключенными. Это
безопасное состояние, а не сбой.

### Зажигание и задний ход: `decodeBody` {#ignition-and-reverse-decodebody}

Функция получает каждый принятый кадр. Она возвращает `false` для любого кадра, который не её или
слишком короткий, и `true` после того, как заполнила `out`. Всегда сначала проверяйте ID и длину;
никогда не читайте дальше длины.

Прошивка не использует байт зажигания вашего автомобиля напрямую. Вы переводите его в
независимый от автомобиля `vehicle::Ignition` (`firmware/lib/core/vehicle_signals.h`):

| Значение | Смысл |
|---|---|
| `OFF` | зажигание выключено или ещё ничего не расшифровано |
| `ON` | зажигание включено, двигатель не работает |
| `ENGINE` | двигатель работает |
| `TRANSITION` | всё остальное, что не «выключено»: прокрутка стартером, выключение, неизвестное вам значение |

Сохраните исходное значение своего автомобиля в `ignitionRaw`. Оно только показывается в консоли и
в панели.

Пример с выдуманного автомобиля этого руководства (кадр `2C0`: байт 2 = зажигание, байт 4 бит 6 =
задний ход):

```cpp
bool decodeBody(const CanFrame& f, vehicle::BodyState& out) {
    if (f.id != ID_BODY || f.len < 4) return false;   // our frame, long enough?
    out.ignitionRaw = f.data[1];                       // byte 2
    switch (f.data[1]) {
        case 0: out.ignition = vehicle::Ignition::OFF; break;
        case 1: out.ignition = vehicle::Ignition::ON; break;
        case 2: out.ignition = vehicle::Ignition::ENGINE; break;
        default: out.ignition = vehicle::Ignition::TRANSITION; break;
    }
    out.reverseGear = (f.data[3] & 0x40) != 0;         // byte 4 bit 6
    return true;
}
```

Как это использует общая логика (`firmware/lib/core/power_policy.h`):

- ACC включён во всех состояниях, кроме `OFF`, поэтому прокрутка стартером не выключает магнитолу.
- ACC выключается через 2,5 с после перехода зажигания в `OFF`.
- Кадр должен приходить постоянно. Если его нет больше 1 с, зажигание считается выключенным
  ([как измерить период](decode.md#how-often-a-frame-comes)).
  На эталонном автомобиле кадр зажигания `0F6` приходит каждые 500 мс (измерено (measured): запись
  `can_20261111_191045.log`). Если ваш кадр зажигания приходит реже раза в секунду, выходы 12 В
  будут отпадать.
- Выход заднего хода включён только при включённом зажигании и свежем кадре.

### Фары: `decodeLights` {#lights-decodelights}

Та же схема: проверить ID и длину, установить `lightsOn`, вернуть `true`. Выход подсветки включён,
только когда зажигание включено **и** кадр фар пришёл за последнюю секунду
([как измерить период](decode.md#how-often-a-frame-comes)). Автомобиль, который
отправляет состояние фар только при изменении, потеряет выход подсветки через одну секунду.

### Парктроники: `decodeParking` {#parking-sensors-decodeparking}

Заполните `vehicle::ParkingState` с тем же смыслом, что на эталонном автомобиле:

| Поле | Смысл |
|---|---|
| `rearStatus`, `frontStatus` | `4` (`PARK_ACTIVE`) = работает. Зуммер использует только сторону со статусом 4. Другие значения: 1 неисправность, 2 выключено водителем, 5 ожидание, 6 не работает |
| `rearLeft` ... `frontRight` | зоны от 0 до 7: 0 = очень близко, 7 = далеко или нет препятствия. Ограничьте свои значения диапазоном 0..7 |
| `soundRequest`, `soundFront` | автомобиль просит звук; спереди (`true`) или сзади |
| `intervalRaw` | `0x00` = непрерывный сигнал, `0x3F` = без сигналов, значения между ними = всё ближе и ближе |

Начните с `out = vehicle::ParkingState();`, чтобы каждое поле, которое вы не заполняете, имело своё
значение "ничего" (зоны 7, статус 0).

Что с этим делает устройство (`firmware/lib/core/parking_beeper.h`):

- оно подаёт сигналы с первой зоны ниже 7 на активной стороне, даже если автомобиль не просит звук;
  темп задаёт ближайшая зона;
- непрерывный сигнал оно включает **только** когда установлен `soundRequest` и `intervalRaw` равен
  `0x00`. Если ваш автомобиль не сообщает интервал, вычисляйте его по зоне, как это делает шаблон;
- оно замолкает, если кадр парктроников не приходил 400 мс. На эталонном автомобиле кадр приходит
  каждые 100 мс.

### Данные автомобиля для экрана магнитолы {#car-data-for-the-radio-screen}

Семь необязательных функций, у всех одни правила: сначала проверьте ID и длину, заполните
нейтральный тип, установите его флаг `valid`, верните `true` (или биты страницы либо изменения).
`firmware/lib/car_example/profile_example.cpp` показывает `decodeDoors` и `decodeTrip`.

- `decodeDoors` -> `DoorState`: `open` содержит биты `DOOR_DRIVER`, `DOOR_PASSENGER`,
  `DOOR_REAR_LEFT`, `DOOR_REAR_RIGHT`, `DOOR_BOOT`, `DOOR_BONNET`; `anyOpen` = предупреждение
  автомобиля об открытой двери. Возвращайте `true`, только когда кадр что-то сообщает о дверях.
- `decodeTrip` -> `TripData`: верните `TRIP_NOW`, `TRIP_1` или `TRIP_2` для страницы, которую
  обновил кадр.
- `decodeOutsideTemp` -> `OutsideTemp`, в половинах градуса Цельсия.
- `decodeEcoMode` -> `EcoMode`: автомобиль вот-вот отключит потребители.
- `decodeClimate` -> `ClimateState`: температуры в половинах градуса (0 = нет значения),
  вентилятор 0..15, флаги `AIR_*`.
- `decodeSteering` -> `SteeringAngle`: сырое значение в кодировке эталонного автомобиля.
- `decodeSettings` -> `VehicleSettings`: для каждого пункта `at(SettingId::...)` значение `value`,
  `known` (ваш последний кадр его сообщил) и `present` / `presentKnown` (у автомобиля есть этот
  пункт). Верните `SETTINGS_VALUES` и / или `SETTINGS_PRESENT`.

Функции с аргументом `io` (бортовой компьютер, климат-контроль, двери, настройки) получают
состояние, которое декодер хранит между кадрами. Меняйте только то, что сообщает ваш кадр, чтобы
несколько кадров могли сложиться в одно состояние.

### Кнопки: таблица `keys` {#buttons-the-keys-table}

Одна строка — одна кнопка, которая "нажата, пока есть битовый шаблон":

```cpp
{canId, byteIndex, mask, value, KeyId::...}
```

Кнопка считается нажатой, пока в кадре `canId` выполняется `(data[byteIndex] & mask) == value`.
Правила из кода (`firmware/lib/core/car_profile.h`, `firmware/lib/app/xp_keys.h`):

- порядок строк — это порядок сравнения и порядок событий для магнитолы;
- используется не больше 32 строк;
- кадр короче `byteIndex + 1` для этой строки пропускается;
- строка, шаблон которой присутствует, когда ничего не нажато, сообщает о кнопке, удерживаемой всё
  время. С `value` = `0x00` это случается легко; давайте каждой строке шаблон, который даёт только
  нажатие;
- нажатие = одно событие сразу, затем каждые 200 мс "удерживается", пока шаблон держится, затем
  "отпущена".

Два способа, которыми автомобиль кодирует кнопки; оба встречаются на практике:

```cpp
// one bit per button (template car: byte 1 bit 0 = volume +, bit 1 = volume -)
{0x200, 0, 0x01, 0x01, KeyId::VOLUME_UP},
{0x200, 0, 0x02, 0x02, KeyId::VOLUME_DOWN},

// a button number in a group of bits (tutorial car: byte 1 bits 3-0 = 1, 2, 3, ...)
{0x1F0, 0, 0x0F, 0x01, KeyId::VOLUME_UP},
{0x1F0, 0, 0x0F, 0x02, KeyId::VOLUME_DOWN},
```

Эталонный профиль тоже использует второй способ: в кадре `21F` байт 1 маска `0C` даёт громкость +
(`08`), громкость - (`04`) и обе вместе, без звука (`0C`) (измерено: записи
`can_20261111_190817.log` и `can_20261111_191045.log`, CAN и линия CAN-адаптера к магнитоле на
одних часах).

Имена (`KeyId`) — логические кнопки. Какой код магнитола получает для каждого имени, решает
протокол магнитолы: см. [Сопоставление с магнитолой](radio-mapping.md).

### Поворотные ручки: таблица `knobs` {#rotary-knobs-the-knobs-table}

Ручка — это 8-битный счётчик в одном байте кадра:

```cpp
{canId, byteIndex, onIncrease, onDecrease}
```

Шаг счётчика +1 — один щелчок `onIncrease`, -1 — один щелчок `onDecrease`. На кадр сообщается не
больше 4 щелчков, и используется не больше 4 строк ручек. Первый кадр только задаёт начальное
значение. Если ваша ручка считает вниз, когда вы вращаете её "вперёд", поменяйте два имени местами,
как это делает эталонный профиль для кадра `21F`.

## Шаг 4: соберите {#step-4-build-it}

Ваш профиль выбирается тремя флагами сборки, без правок в `src/`. В файле
`firmware/platformio_override.sample.ini` уже есть окружение для профиля с именем `mine`:

1. Скопируйте `firmware/platformio_override.sample.ini` в `firmware/platformio_override.ini`. Новый
   файл не отслеживается Git; `platformio.ini` загружает его автоматически.
2. Если ваш профиль называется не `mine`, измените раздел `listen_mycar`, чтобы он выглядел так,
   с вашим именем вместо `<name>` и `<Name>`:

    ```ini
    [env:listen_mycar]
    extends = env:listen_wifi
    lib_deps = car_<name>
    build_flags =
        ${env:listen_wifi.build_flags}
        -DCAR_PROFILE=CUSTOM
        '-DCAR_PROFILE_CUSTOM_HEADER="profile_<name>.h"'
        -DCAR_PROFILE_CUSTOM_OBJECT=kCar<Name>
    ```

    `lib_deps` нужен: PlatformIO не следует за `#include`, который приходит через макрос. Раздел
    `listen_mine` в том же файле относится к вашей собственной плате, а не к автомобилю; оставьте
    его.
3. Соберите, из папки `firmware`:

    ```bash
    uvx platformio run -e listen_mycar
    ```

    Ожидаемый результат: сборка заканчивается `SUCCESS`, а список зависимостей вверху показывает
    `|-- car_mine @ 1.0.0`. Другие сообщения: см. [Частые ошибки](#common-mistakes).
4. Прошейте и откройте консоль:

    ```bash
    uvx platformio run -e listen_mycar -t upload
    uvx platformio device monitor
    ```

    Ожидаемый результат: `# profile: car=mine radio=xp` при запуске. Порт и режим загрузчика:
    [Прошивка](../quick-start/flash.md).

`listen_mycar` — сборка только для прослушивания в параллельном режиме (рядом с адаптером): она
расшифровывает ваш автомобиль, подаёт сигналы парктроников из динамика устройства и выводит строки
консоли, но ничего не отправляет в магнитолу и держит выходы 12 В выключенными. В консоли введите
`keys`, чтобы выводить каждое событие кнопки, `dump` — чтобы выводить каждый кадр CAN.

### Режим декодера с вашим профилем {#decoder-mode-with-your-profile}

Чтобы управлять магнитолой (кадры UART, ACC, выходы подсветки и заднего хода), добавьте второй
раздел в свой `platformio_override.ini`. Этот раздел успешно собрался при прохождении руководства:

```ini
[env:decoder_mycar]
extends = env:decoder_wifi
lib_deps = car_mine
build_flags =
    ${env:decoder_wifi.build_flags}
    -DCAR_PROFILE=CUSTOM
    '-DCAR_PROFILE_CUSTOM_HEADER="profile_mine.h"'
    -DCAR_PROFILE_CUSTOM_OBJECT=kCarMine
```

> [!CAUTION]
> **Режим декодера управляет магнитолой и выходами 12 В**
>
> Прошивайте сборку декодера только после того, как профиль прошёл проверку на ПК и на столе, и
> только при отключённом CAN-адаптере: два передатчика на одной линии UART и два
> источника ACC означают выходы, работающие друг против друга. Сначала прочитайте
> [Подключение к магнитоле](../../en/install-in-car/radio-connection.md) и
> [Первая поездка](../../en/install-in-car/first-drive.md). На шине CAN автомобиля эта сборка
> по-прежнему только слушает.

### Что намеренно не собирается {#what-does-not-build-on-purpose}

| Попытка | Результат |
|---|---|
| `decoder_tx_wifi` с `-DCAR_PROFILE=CUSTOM` | `#error "CAN transmit is not allowed with CAR_PROFILE=CUSTOM ..."` (опробовано при прохождении руководства) |
| `decoder_tx_wifi` с `-DCAR_PROFILE=GENERIC` | `#error "CAN transmit is not allowed with CAR_PROFILE=GENERIC ..."` (проверяется `tools/check_tx_profile_lock.sh`) |
| `-DCAR_PROFILE=EXAMPLE` в любом окружении | `#error "CAR_PROFILE=EXAMPLE is a template for the host tests only ..."` |
| `CUSTOM` без флага заголовка или объекта | `#error "CAR_PROFILE=CUSTOM needs ..."` |

## Не начинайте с эталонного профиля {#do-not-start-from-the-reference-profile}

Можно было бы скопировать `firmware/lib/car_psa_aee2010/` вместо шаблона. Учтите, что тогда
произойдёт: если ваш профиль оставит эталонные функции, он расшифровывает ID кадров эталонного автомобиля
(двери, настройки, бортовой компьютер, климат). Если он оставит ещё и `psa::decodeBodyState` для
зажигания, прошивка будет считать ваш автомобиль автомобилем PSA AEE2010 и при изменении настроек,
и в условиях передачи (`firmware/lib/app/decoder.cpp`, `Decoder::begin`). Это верно только для автомобиля, у которого измерения подтвердили те же
кадры. Считайте каждый кадр другого автомобиля **не проверенным**, пока не записали его, даже на
близком родственнике эталонного автомобиля.

## Частые ошибки {#common-mistakes}

| Признак | Причина |
|---|---|
| `fatal error: profile_mine.h: No such file or directory` | не изменено поле `name` в `library.json` или нет `lib_deps` |
| `# can=FAIL` при запуске, красный светодиод | `canBitrate` не входит в шесть поддерживаемых скоростей |
| кнопка всё время числится удерживаемой | её шаблон `mask` / `value` присутствует в покое |
| кнопки не на тех битах | `byteIndex` отсчитан с 1, а не с 0 |
| выход подсветки отпадает через 1 с | кадр фар не повторяется хотя бы раз в секунду |
| нет сигнала, но зоны меняются | статус стороны не `4` (`PARK_ACTIVE`) |

Далее: [Проверьте свой профиль](test-your-profile.md).
